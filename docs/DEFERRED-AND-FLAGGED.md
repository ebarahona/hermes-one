# Scope ledger — delivered, ratified, and planned

The single running registry of **what is delivered, what has been ratified as a decision, and what is
scheduled for a later increment** in the `hermes-one` build. Scope is tracked explicitly here rather
than settled ad hoc in code: when the build reaches a point where the design leaves a choice
open, or where a capability belongs to a later increment, it is recorded as a row with its target
rather than improvised.

This is the reason the boundary between delivered and scheduled is always legible. **36 rows below
are complete and marked 🟢**, each with the commit and date that closed it; the remainder carry a
defined target.

**2026-07-22:** platform-wide engineering review and hardening cycle — rows below carrying that date
were completed in that cycle. Status as of 2026-07-22: **0 🔴 open** (S0a applies only under a
multi-instance posture that is not yet deployed) · **48 🟡 scheduled** · **12 ⚪ cosmetic**.

**How to use this doc**

- Every scoped item in the code (search markers: `flagged`, `follow-up`, `Open Questions`) has a row
  here, so the delivered surface and the scheduled surface are both explicit.
- Each row: **what** the item covers · **why** it sits where it does (design reference / rationale) · **where**
  it lives in the tree · **target** (what completion looks like) · **status**.
- On completion, the row flips to 🟢 with its commit and date. Completed rows are retained for a
  release cycle — they record how each decision was carried through.
- New items are appended under the right area. The running narrative lives in the project's session
  context notes (maintained outside this repository); this doc is the checklist they point to.

Status: 🟢 delivered or ratified · 🔴 must land before the affected posture ships · 🟡 scheduled
increment · ⚪ cosmetic.

## LoopBack composition layer (DECIDED 2026-07-14: build to design)

`@hermes-one/contracts`), `PlatformBindings` + `tenantKey` + `PlatformExtensionPoints`,
`PlatformComponentBoundary`, `PlatformApplication`, `bootstrap()`, and five edge components —
Persistence (one shared pool + lifecycle observers owning the fail-closed RLS boot gate),
Observability, CapabilityRegistry (provider adapters discovered via `extensionFor`-tagged bindings —
the real LB4 extension-point idiom, no hardcoded lists), RuleRuntime, PolicyRuntime. The
**activity-worker composition root is migrated** (config→bind→components→observers→resolve-activities).
